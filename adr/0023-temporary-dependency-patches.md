# 23. Temporary Dependency Patches

Date: 2026-08-31

## Status

Accepted

## Context

Pepr keeps dependencies current through Dependabot and scheduled peer dependency update workflows. Sometimes a small upstream bug blocks a valid update before the fix is released.

The motivating case is `thread-stream`, a transitive dependency of `pino`. `@types/node@26` removed the deprecated `worker_threads.TransferListItem` alias, but `thread-stream@4.2.0` still referenced it in `index.d.ts`. TypeScript failed with:

```text
error TS2694: Namespace '"worker_threads"' has no exported member 'TransferListItem'.
```

Upstream issue pinojs/thread-stream#228 and PR pinojs/thread-stream#233 identify the fix: replace `workerThreads.TransferListItem[]` with `workerThreads.Transferable[]`. No released package contained that fix when we made this decision.

We need a standard way to unblock dependency updates without weakening compiler checks, pinning unrelated versions, or maintaining forks. The workaround must also preserve Pepr's package boundary: a fresh module should build after installing a published or packed Pepr package, without module authors knowing about repo-local patch state or approving extra install scripts.

## Compatibility Goals

- Dependency updates should not break module authors unless the generated module template has an intentional breaking change.
- Pepr can use `@types/node@26` with a temporary workaround, but modules generated by Pepr must still build.
- Module authors should not add `patch-package` or approve Pepr lifecycle scripts for a transitive bug introduced by Pepr's dependency graph.
- CI must test the packed-package path: install the Pepr tarball into a fresh module, then run `pepr build` without repo-local patch access.
- Removal needs a clear cue. For this case, remove the workaround when Pepr bumps `pino` to a version that resolves the fixed `thread-stream` declaration.

## Decision

We will use [`patch-package`](https://www.npmjs.com/package/patch-package) for small, temporary dependency patches when:

- An upstream package blocks a dependency update or CI check.
- The patch is narrow, reviewable, and low-risk.
- An upstream issue, PR, release note, or other clear removal condition exists.
- Normal CI can verify the patch.

Patch files live under `patches/`. Pepr runs `patch-package` before repo builds and verifies it in CI with `npx patch-package --error-on-fail`.

Pepr will not ship temporary dependency patches through package `postinstall` unless there is no safer option. Some consumers and CI systems block new install scripts, so install-time patches can make an otherwise compatible Pepr patch release fail during installation. When generated modules need a compatibility fix, prefer applying the smallest possible fix inside the Pepr command path that needs it.

For the `thread-stream` case, the local patch applies the same one-line declaration change proposed upstream:

```diff
-  emit(eventName: 'message', message: any, transferList?: workerThreads.TransferListItem[]): boolean
+  emit(eventName: 'message', message: any, transferList?: workerThreads.Transferable[]): boolean
```

We will not use this mechanism for broad rewrites, behavior changes, security fixes that need deeper review, or changes that should be maintained in a fork.

## Lessons Learned

- Repo-local patching can make Pepr pass while generated modules still fail. The real boundary is a packed or published Pepr package installed into a separate module project.
- `npx --package <tarball> pepr init` can run outside a package root. Use `INIT_CWD` as the install target only when it contains `package.json`; otherwise use Pepr's package root.
- Dockerfiles that run `npm run build` need `patches/` available before `prebuild` runs. After build, use `npm prune --omit=dev --omit=peer`, avoid commands that reinstall dev dependencies, and remove patch files from final image content if they are not needed at runtime.
- `npx patch-package --error-on-fail` proves the patch applies. A generated-module tarball install plus `pepr build` proves consumer compatibility.
- Generated modules should inherit as few Pepr dev dependencies as practical. When they inherit a tool or type dependency, Pepr owns making that default buildable.
- Package lifecycle scripts are part of Pepr's consumer surface. Adding a new install script can break repos that enforce explicit script approval.

## Consequences

- Dependency updates can proceed while small upstream fixes are pending.
- Patch files are reviewed code, not hidden `node_modules` state.
- Pepr does not require consumers to run patch-package or approve new Pepr install scripts for this workaround.
- CI proves both patch applicability and generated-module compatibility.
- We keep `skipLibCheck` disabled and avoid downgrading unrelated type packages.
- Each patch needs an upstream reference and removal tracker. If it stops applying, CI forces a decision: update it, remove it, or choose another fix.

## Alternatives Considered

**Wait for upstream release.** This avoids local patching, but blocks dependency updates for an unknown time.

**Pin or downgrade the conflicting dependency.** This can be acceptable for short-lived updates. Here, it would hold back `@types/node@26` and hide the compatibility problem.

**Set `skipLibCheck: true`.** This bypasses the TypeScript error, but weakens declaration checking across the project.

**Maintain a fork.** A fork is too heavy for a one-line declaration fix and creates long-term ownership.

**Use package postinstall.** This applies patches early, but adds install-script approval burden to downstream repos and can break CI before `pepr build` runs.

## Follow-up

For the `thread-stream` workaround, remove `patches/thread-stream+*.patch`, remove `patch-package` if no other patches remain, remove the build-time compatibility patch, and remove patch-specific CI when Pepr bumps `pino` to a version that resolves the declaration fix and `npm run build` passes without the patch.
